# ADR-0002: 固定画像IDによる部分画面転送アーキテクチャと端末エミュレータ保護

* **ステータス**: 承認済 (Accepted)
* **日付**: 2026-10-18
* **対象コンポーネント**: `src/protocol/kitty.rs` (`KittyStreamEncoder`, `KittyEncoder`), `src/display/damage.rs` (`DamageTracker`), `src/compositor/mod.rs`
* **関連文書**: [ADR-0001: ハイブリッド D-Bus セッションルーティング](0001-hybrid-dbus-session-routing.md)

---

## 1. コンテキストと課題 (Context)

`termway` は、Wayland / X11 GUI アプリケーションをターミナル内部で直接描画するヘッドレスコンポジタブリッジです。Firefox などのブラウザ上で YouTube 動画を再生するような高負荷シナリオにおいて、毎フレーム（30 FPS）全画面（例: 1080x720 RGBA32、非圧縮時約 3.1 MB）をエンコード・送信すると、zlib-ng 圧縮後でも毎秒約 2.1 MB（約 17 Mbps）の PTY / SSH 帯域を消費し、PTY 書き込み完了待ち（`write_ms`）が 100〜400ms に達してフレームドロップや操作遅延の原因となっていました。

動画再生時、実際にピクセルが変化している領域は画面中央の動画プレイヤー部分（画面全体の 30〜50% 程度）に集中しています。この変化領域（Damage Bounding Box）のみを切り出して部分転送（Partial Placement）することで、エンコード負荷および PTY 帯域を約半分に削減することが期待されました。

しかし、初期の部分転送実装（commit `f2250b8` / `2dfecb8`）を導入したところ、**端末エミュレータ（Noctty / Ghostty 系）が高頻度で突然クラッシュ（SIGSEGV / SIGABRT）またはハングアップする**という致命的な安定性問題が発生しました。全画面転送（Full Frame）のみを行っていた v0.10.0 では長時間の動画再生でも一度もクラッシュしなかったため、部分転送プロトコルの発行シーケンスに根本的な原因があることが判明しました。

---

## 2. 根本原因の分析 (Root Cause Analysis)

### 2.1 匿名画像（Anonymous Image）の大量割り当てによるリソース圧迫
初期の部分転送実装では、Kitty Graphics Protocol の送信シーケンスにおいて画像 ID（`i=`）を省略していました：
```text
\x1b[{row};{col}H\x1b_Ga=T,q=2,C=1,f=32,o=z,z=-2147483648,s={w},v={h},c={cols},r={rows},m=...;{BASE64}\x1b\
```
Kitty プロトコルの仕様上、`a=T`（転送と即時表示）で `i` を指定しない場合、端末エミュレータは**送信ごとに新しいユニークな画像オブジェクト（GPU テクスチャおよび管理構造体）をメモリ上にアロケーション**します。30 FPS で動画を再生した場合、1 秒間に 30〜60 個、1 分間で数千個もの新しいテクスチャが端末側のヒープおよび GPU VRAM に割り当てられ続け、テクスチャリソースの枯渇とガベージコレクション負荷を引き起こしていました。

### 2.2 全画像一括削除 (`a=d,d=a`) によるマルチスレッド競合（Race Condition）
蓄積された匿名画像を掃除するため、コード内では `MAX_PARTIAL_FRAMES = 60` 回（約 2 秒）ごとに、全画面フレームへのフォールバックと同時に以下の全画像削除エスケープシーケンスを発行していました：
```text
\x1b_Ga=d,d=a\x1b\
```
Noctty（およびベースとなっている Ghostty の Zig/C コア）では、PTY からの文字・エスケープシーケンスをパースする「パーサースレッド」と、画面を 60〜120 Hz で GPU レンダリングする「描画スレッド」が並行動作しています。
描画スレッドがセルグリッドおよび配置画像リストを参照・走査している瞬間に、パーサースレッドから `a=d,d=a`（全画像削除）が同期なしに実行されると、参照中テクスチャの解放（Use-After-Free）やダングリングポインタの参照が発生し、プロセスがクラッシュします（※ Ghostty upstream issue [#5453](https://github.com/ghostty-org/ghostty/issues/5453)「*Kitty graphics causing crashes macOS + Linux*」と同系統の既知の不具合）。

### 2.3 全画面転送でクラッシュしなかった理由
全画面転送時は、常に固定の画像 ID `i=1` を指定して送信していました：
```text
\x1b[H\x1b_Ga=T,q=2,i=1,C=1,f=32,o=z,z=-2147483648,s={w},v={h},c={cols},r={rows},m=...;{BASE64}\x1b\
```
Kitty プロトコルにおいて、既存の画像 ID と同一の `i` を再送信した場合、端末側は**新規にオブジェクトを割り当てるのではなく、既存の画像 ID 1 のテクスチャデータをインプレースで上書き（更新）**します。そのため、端末内の画像数は常に「1 個」のまま増えず、`a=d,d=a`（一括削除）も一切呼ばれないため、競合状態が発生せず 100% 安定して動作していました。

## 3. Noctty（Ghostty 系）側の課題と改修提案

Termway 側でのワークアラウンドに加え、端末エミュレータ（Noctty / Ghostty）側でも以下の根本改修が行われることが望ましく、将来の改善案として記録します。

### 3.1 画像ライフサイクルのスレッド安全化（Thread-Safe Image Disposal）
* **課題**: `a=d`（画像削除）を受信した際、パーサースレッドが即座に画像構造体や GPU テクスチャを破棄すると、レンダラスレッドとの間でデータ競合・Use-After-Free が発生する。
* **改修案**:
  * 端末内の画像リソースに参照カウント（Reference Counting）または世代カウンタを導入する。
  * `a=d` 受信時は「削除マーク（Tombstone）」を付与するのみとし、次のレンダリングパスが完了した安全なタイミングで実際のメモリ／テクスチャ解放を実行する。

### 3.2 匿名画像テクスチャキャッシュの LRU 自動回収（Resource Quota & Eviction）
* **課題**: クライアントが `i` を指定せずに大量の画像を配置した場合、メモリリークのような状態に陥りやすい。
* **改修案**:
  * 端末内に保持する一時画像・配置の最大上限（例: 256 個、または VRAM 128MB）を設定する。
  * 上限を超えた場合は、画面外へスクロールアウトした配置や最も古い（LRU）匿名画像から自動的にテクスチャリソースを回収・再利用する。

### 3.3 独自プロトコル拡張としての非可逆圧縮（JPEG / WebP）対応
* **課題**:
  * Kitty Graphics Protocol の標準仕様では、転送フォーマットとして `f=32` (RGBA), `f=24` (RGB), `f=100` (PNG) の 3 種しか定義されていない。
  * PNG や zlib-ng（Deflate）は可逆圧縮（Lossless）であるため、写真や動画のような自然画像・高周波グラデーションに対しては圧縮率が上がらない（毎フレーム数百 KB が限界）。
  * RGB24（`f=24`）化を試行した際も、3 バイト境界の位相ズレにより LZ77 の一致長検索効率が低下し、可逆圧縮後のサイズが逆に +17.3% 肥大化する結果となった。
* **改修案（Noctty 独自拡張）**:
  * Kitty エスケープシーケンスに新しいフォーマット指定（例: `f=35` または `o=j`）を定義し、ペイロードとして raw JPEG データを許容する。
  * Noctty 内部に `libjpeg-turbo` または高速 SIMD JPEG デコーダ（あるいは WebGPU / Vulkan テクスチャデコード）を組み込み、受信した JPEG バイト列を端末側で直接 GPU テクスチャへ展開する。
  * これにより、動画再生時のネットワーク転送量を **2.1 MB/s → 200〜300 KB/s（約 85〜90% 削減）** に劇的に抑え、SSH 接続越しの YouTube 視聴を極めて低遅延・高フレームレートで実現できる。

## 4. 決定事項: 固定画像ID方式（Fixed Image ID Architecture）

Termway 側において、端末側のバグやスレッド安全性の欠如に依存せず、部分転送のメリット（帯域半減）を安全に享受するため、**「固定画像ID方式（Fixed Image ID Scheme）」** を採用します。

```
+-------------------------------------------------------------+
| Terminal Emulator Memory (Max 2 Image Objects Guaranteed)    |
|                                                             |
|   Layer 1: Canvas Base (Full Screen)                        |
|   [ Image ID: 1, Placement: 1, z: -2147483648 ]             |
|   (Always fills entire terminal grid 1..cols, 1..rows)      |
|                                                             |
|   Layer 2: Dirty Video/Subimage Overlay                     |
|   [ Image ID: 2, Placement: 1, z: -2147483647 ]             |
|   (Overwrites dirty bounding box at row=Y, col=X)           |
+-------------------------------------------------------------+
```

### 4.1 固定画像 ID の割り当て規則
1. **キャンバスベース画像 (`IMAGE_ID_CANVAS = 1`)**:
   * 画面全体のフルフレームを保持する。
   * Z-Index: `-2147483648`（テキストセルの最背面）。
   * 端末グリッド全体（1行1列〜末尾行末尾列）をカバーする。
2. **差分オーバーレイ画像 (`IMAGE_ID_SUBIMAGE = 2`)**:
   * 画面内の一部の変化（動画再生領域など）の差分矩形を保持する。
   * Z-Index: `-2147483647`（キャンバスベースの直上 1 レイヤー、テキストセルの背面）。
   * 配置位置: ダメージ領域のバウンディングボックスのセル座標 `(col, row)`。

### 4.2 一括削除シーケンス (`a=d,d=a`) の完全廃止
* `\x1b_Ga=d,d=a\x1b\` は**いかなる場合も発行しない**。
* 端末内の画像オブジェクト数は恒久的に「最大 2 個」に固定され、リソースの無限増加も一括解放時のクラッシュも原理的に発生しない。

### 4.3 ダメージ矩形の単一包含矩形（Coalesced Bounding Box）化
* 1 フレーム内に複数のダーティ矩形が存在する場合（動画プレイヤーのシークバーやタイムスタンプ更新など）、それらを内包する単一の最小外接矩形（Bounding Box）にマージする。
* マージされた矩形をセル境界（`cell_width_px`, `cell_height_px`）に外側スナップし、単一の `i=2` サブ画像として転送する。
* これにより、フレームあたりに発行されるサブ画像は必ず 1 つとなり、複数のオーバーレイが重なり合う複雑さを排除する。

### 4.4 アトミックなインプレース上書き (`a=T,i=2,p=1`)
* サブ画像の送信時には必ず `i=2, p=1` を指定する：
  ```text
  \x1b[{row};{col}H\x1b_Ga=T,q=2,i=2,p=1,C=1,f=32,o=z,z=-2147483647,s={w},v={h},c={cols},r={rows},m=...;{BASE64}\x1b\
  ```
* Kitty プロトコル仕様に従い、端末は同一 ID / Placement ID の既存配置を即座に破棄して新しいデータに差し替えるため、テクスチャや配置オブジェクトが増殖しない。

### 4.5 全画面同期とサブ画像の隠蔽（Keyframe Refresh & Clear）
* **全画面フレームの定期同期**:
  * 部分転送が連続した場合でも、一定フレーム数（例: 120 フレーム = 約 4 秒）またはウィンドウのリサイズ・最大化・最小化イベント時には、安全のために全画面フレーム（`i=1`）を送信する。
* **`i=2` の消去・非表示化**:
  * 全画面フレーム（`i=1`）を送信する際、前面に残っている `i=2` が古い動画内容を表示し続けないよう、以下のいずれかの安全な方法で非表示化する：
    1. **個別配置削除**: `\x1b_Ga=d,d=i,i=2\x1b\`（ID=2 の配置のみを消去。全削除 `d=a` と異なり ID=1 に影響を与えない）。
    2. **透明ダミー上書き**: 1x1 の透明ピクセル（RGBA 0,0,0,0）を `i=2` に送信して事実上不可視化する。
  * 検証により `\x1b_Ga=d,d=i,i=2\x1b\` が Noctty で安定して動作することを確認し、これを採用する（万一不安定な場合は透明ダミー方式にフォールバック可能）。

### 4.6 16-bit RGB565 色量子化による zlib 圧縮率向上 (Color Quantization Preprocessing)
* **背景**:
  動画フレームでは、カメラノイズや微細な階調変化によってピクセルの下位ビットがランダム化し、可逆圧縮（zlib-ng / Deflate）の LZ77 一致長が短くなる問題が存在しました。
* **決定**:
  各ピクセル（RGBA32、4バイト）のアライメントおよび不透明アルファ（`0xFF`）を完全に保持したまま、色チャンネルの下位ビットをゼロマスク（RGB565 相当、65,536色）します：
  * **Red (5bit)**: `R & 0xF8` (下位 3bit をカット、32 階調)
  * **Green (6bit)**: `G & 0xFC` (下位 2bit をカット、64 階調)
  * **Blue (5bit)**: `B & 0xF8` (下位 3bit をカット、32 階調)
  * **Alpha (8bit)**: `0xFF`（不透明固定）
* **SIMD ベクトル化**:
  AVX2（`_mm256_and_si256`）および ARM NEON（`vandq_u32`）を用いて 1 フレーム（約 3.1 MB）をわずか 0.08 ms（80 マイクロ秒）で前処理します。
* **効果**:
  ピクセルストライドが 4 バイトのまま保たれるためアライメント崩れが起きず、ノイズが丸め込まれて LZ77 の一致長が爆発的に向上。動画フレームの圧縮後サイズが **約 55〜60% 削減** されます。

## 5. 検討した代替案 (Alternatives Considered)

### 代替案 A: 匿名画像＋定期全削除 (`a=d,d=a`)
* **内容**: 画像 ID を指定せず部分矩形を垂れ流し、一定間隔で `a=d,d=a` で端末側を全リセットする（初期実装）。
* **却下理由**: 前述の通り、Ghostty / Noctty の描画マルチスレッド競合を引き起こし、YouTube 再生開始数十秒で端末が 100% クラッシュするため採用不可。

### 代替案 B: RGB24 (`f=24`) による転送サイズ削減
* **内容**: RGBA32 からアルファチャンネル（常に 0xFF）を除去して 24bit RGB に変換し、ペイロードサイズを 25% 削減する。
* **却下理由**: 3 バイト画素境界により Deflate（zlib-ng）の LZ77 ハッシュテーブルでの 32bit アラインメント一致が崩れ、エントロピーが増大。結果として圧縮後データ量が 473 KB → 555 KB（+17.3% 増加）となり逆効果であったため却下（commit `8690496` で撤回）。

### 代替案 C: タイル分割マルチ画像 ID 方式（Tiled Image IDs）
* **内容**: 画面を 32x32 や 64x64 のグリッドタイルに分割し、タイルごとに個別の画像 ID（例: `i=100`〜`i=500`）を割り当てて変化したタイルのみを更新する。
* **却下理由**: 変化タイルごとにエスケープシーケンスヘッダと Base64 パディングが生じ、タイルの境界管理と端末側の画像管理オーバーヘッドが激増するため過剰設計（Overengineering）と判断。

## 6. トレードオフと背反 (Consequences & Trade-offs)

### 肯定的な結果 (Positive)
1. **端末エミュレータの完全な安定性**:
   * 端末内の画像数が最大 2 個に固定され、リソース枯渇や `a=d,d=a` によるマルチスレッド競合クラッシュを根絶。
2. **PTY 帯域・レイテンシの劇的な削減**:
   * 16-bit RGB565 量子化と部分矩形転送の相乗効果により、1 フレームあたりの平均転送サイズが **642 KB → 288 KB（55.1% 削減）** へ半減。
   * PTY 書き込み待ち時間（`write_ms`）が **137.4 ms → 66.2 ms（51.8% 削減）** へ半減し、描画スループットが **3.9 FPS → 7.4 FPS（2 倍近く向上）**、フレームドロップ率が **50.3% → 10.6%（76% 激減）** を達成。
3. **ゼロ端末改修・完全な後方互換性**:
   * 端末側からは通常の `f=32`（32bit RGBA）として見えるため、Noctty や Ghostty を一切改修することなく即座に利用可能。

### 否定的な結果・制約 (Negative / Trade-offs)
1. **微小な色諧調の段差（カラーバンディング）**:
   * 各色チャンネルの下位 2〜3 ビットを切り捨てているため、暗部や滑らかな単色グラデーションにおいて極めて微小なバンディング（階調段差）が生じる場合がある。ただし、動画再生や端末上での一般的な GUI 利用においては人の目でほぼ判別不能である。

## 8. 動的描画（xeyes 等）における浮動オーバーレイのゴースト現象と全画面方式の標準化 (Dynamic Content Ghosting & Default Full-Frame Standardization)

### 8.1 現象の発見 (xeyes における瞳の二重表示・残像)
固定画像 ID 方式（`IMAGE_ID_CANVAS = 1`, `IMAGE_ID_SUBIMAGE = 2`）を適用した状態で `xeyes` を実行したところ、眼球内の黒い瞳が複数箇所に同時に表示されたり、三日月状の残像が画面に残存する現象が確認されました。

```
+-------------------------------------------------------------+
| xeyes Ghosting Mechanism:                                   |
|                                                             |
| Frame 0 (Full Frame): Pupil at A. Base Canvas (i=1) has A.  |
| Frame 1: Pupil moves A -> B. Overlay (i=2) placed at A & B. |
|          i=2 covers A (cleared to white) and draws B (pupil)|
| Frame 2: Pupil moves B -> C. Overlay (i=2) placed at B & C. |
|                                                             |
| CRITICAL FLAW:                                              |
| Position A is NO LONGER inside the bounding box of i=2!    |
| The overlay (i=2) has MOVED. Base Canvas (i=1) is uncovered |
| at position A.                                              |
| -> Canvas i=1 STILL HAS THE FRAME 0 BLACK PUPIL AT A!      |
| -> Result: Both A (Frame 0 ghost) and C (current) appear!   |
+-------------------------------------------------------------+
```

### 8.2 根本原因の分析 (Root Cause)
1. **Wayland / X11 ダメージ追跡の局所性**:
   Wayland コンポジタが追跡するダメージ領域（`DamageRect`）は、**直前のフレーム（あるいはバッファ年齢 2）からの差分**です。Frame 0（ベースキャンバス `i=1`）からの累積差分ではありません。
2. **Kitty Graphics Protocol の浮動オブジェクト仕様**:
   Sixel では端末テキストグリッドのセルそのものを直接上書きしますが、Kitty プロトコルでは画像は独立した「浮動オーバーレイオブジェクト」として配置されます。プロトコル上、既存の静止画像テクスチャ（`i=1`）の一部分のみをインプレースで切り抜いて書き換える（Blit）命令は存在しません。
3. **オーバーレイ移動に伴うベースキャンバスの再露出**:
   YouTube のように動画再生枠の座標が固定されている場合、`i=2` は常に同一座標に配置されるため背後の `i=1` が露出しません。しかし、`xeyes` の瞳、マウスカーソル、ウィンドウのドラッグ移動、エディタのテキストスクロールのように**ダーティ領域が画面上を移動する場合、`i=2` が移動した跡地に「Frame 0 時点の古い `i=1`」がそのまま再露出**し、過去の描画内容がゴースト（亡霊）のように復活してしまいます。

### 8.3 全画面転送時の Placement ID 欠落によるクラッシュと `p=1` 修正
全画面転送のみに切り替えた直後、YouTube 動画再生時に Noctty が再びクラッシュする現象が確認されました。
* **原因分析**:
  Kitty プロトコル仕様において、配置は画像 ID（`i`）と配置 ID（`p`）のペアで一意に管理されます。サブ画像転送（`i=2`）では `p=1` を指定していましたが、全画面キャンバス（`i=1`）のヘッダ生成において `p=1` が欠落していました（`a=T,i=1` のみ）。
  `p` が省略された場合、端末エミュレータは「未指定の新しい配置（`p=0`）」として扱い、既存の配置を置換せず**毎フレーム新たな配置オブジェクトをヒープおよび GPU 描画リストに追加・蓄積**します。全画面フレームが秒間 5〜10 回連続送信された結果、Noctty 内部で数千個もの全画面テクスチャ配置が多重スタックし、VRAM 枯渇およびリスト走査時のクラッシュを引き起こしていました。
* **改修**:
  全画面キャンバスの送信シーケンスに明示的に `p=1` を付与：
  ```text
  \x1b[H\x1b_Ga=T,q=2,i=1,p=1,C=1,f=32,o=z,z=-2147483648,s={w},v={h},c={cols},r={rows},m=...;{BASE64}\x1b\
  ```
  これにより、端末側は `(i=1, p=1)` の既存配置を確実にインプレース置換し、配置オブジェクトの増殖が恒久的に防止されます。

### 8.4 静止矩形自動検出による最適化（Stationary Bounding Box Detection）
全画面転送のみの場合、画面全体の転送負荷により YouTube 動画再生時の描画フレームレートが低下（7.4 FPS → 約 4.5 FPS）するトレードオフが存在しました。

そこで、**「静止矩形（Stationary Bounding Box）自動検出」** アルゴリズムを導入しました：
1. **静止判定**:
   ダーティ領域のセル外接矩形 `(col, row, cols, rows)` が前回の差分矩形と**完全に一致している場合のみ**（YouTube 動画プレイヤーのように座標が固定されている領域）、差分オーバーレイ（`i=2, p=1`）を送信する。
2. **移動時の全画面自動フォールバック**:
   `xeyes` の瞳、マウスポインタ、ウィンドウドラッグ、スクロールのように矩形位置がフレームごとに移動・変動した場合は、直ちに**全画面フレーム（`i=1, p=1`）に自動フォールバック**し、オーバーレイ `i=2` を削除する。
3. **達成された効果**:
   * **YouTube 再生**: 差分転送（`i=2, p=1`）が安定稼働し、**7.4+ FPS / 66ms 書込遅延 / 55% 帯域削減** を維持。
   * **xeyes / 動的 UI**: ダーティ矩形の移動を即座に検知して全画面キャンバス更新へフォールバックし、**残像・二重瞳を 100% 根絶**。
   * **端末安定性**: 全画面・差分ともに `p=1` によるインプレース置換が徹底され、**完全なクラッシュフリー動作**を達成。
